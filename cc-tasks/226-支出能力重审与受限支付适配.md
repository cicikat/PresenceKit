# Brief 226 · 支出能力重审与受限支付适配（替代 Brief 63）

> 状态：`planned`，默认不启用任何自动付款。
>
> 本单替代已退役的 Brief 63。目标不是立即让 agent 花钱，而是先把余额观测、账本、
> 明确授权和支付适配器边界做成可验证的闭环；任何资金执行都必须另过本单的准入门槛。

## 1. 当前事实与非目标

- Brief 57 当前只有只读余额检查、支出账本和人工提醒；不得描述为“自动充值已完成”。
- 预留 `GET /spend/mandates` 读面已删；confirm/reject writer、购买执行器和商家 adapter 尚不存在。历史 `mandates.jsonl` 不由代码清掉。
- 不做浏览器自动下单、扫码支付、短信/OTP/3-D Secure 代填、订阅扣费、转账、提现、投资或赌博。
- 不在后端保存卡号、支付密码或完整私钥；所有秘密只进受控的本地配置/平台托管密钥。

## 2. 阶段 A：修复 Brief 57 并完成 soak

1. 找出余额 provider 当前 `check_failed` 的根因，先让一次手动 `/spend/check` 产生 `observed`。
2. 从首次成功观测开始重新计时 30 天；每日检查、失败分类、账本写入和通知链均需可观测。
3. 验收条件：无 capped 误判、无审计事故、无账本写失败遗漏；`confirmed` 只能代表真实且已授权的外部结果。
4. soak 期间保持人工充值/人工购买，`auto_execute=false`，不接入真实支付写 API。

## 3. 阶段 B：支付载体决策（先小额、可撤销）

按优先级评估：

1. 平台预充值/API 余额：优先，商户边界清晰，适合先做 adapter 和幂等回执。
2. 专用低余额支付账户或虚拟卡：只有在发卡方支持冻结额度、商户限制和即时停用时考虑；不把主银行卡交给 agent。
3. 礼品卡/一次性额度：适合实验，但必须确认退款、过期和地域限制。

每种载体必须记录：所有者、最高余额、单笔上限、日/月上限、允许商户、撤销方式、失败回执、人工暂停开关。

## 4. 阶段 C：Cloudflare Wallet 评估

Cloudflare Wallet 作为候选的“机器支付 API/内容”通道，不作为当前购物卡或银行卡替代品：

- 当前可用范围以官方文档为准；钱包 handle 预留不等于已经能收、存、发资金。
- 未来 Account Wallet → Virtual Wallet 的额度、商户和单笔限制，与本项目的 mandate/budget/audit 模型方向一致。
- 仅在 Cloudflare 正式开放、账户地区与合规条件确认、并提供可测试 sandbox/testnet 后，另写 adapter 子工单。
- 首个 adapter 只允许 x402/MPP 等明确机器支付的 API、MCP 工具或数字内容；不扩展到实体商品网站。
- 私钥/API 凭据不得进入 prompt、意向单、日志、客户端或仓库；支付挑战中的金额、收款方、网络和回执必须结构化校验。

## 5. 阶段 D：受限意向单与人工确认（独立子工单）

只有 A、B 完成并由用户明确开启后，才允许施工：

1. 选品阶段零支付权限，只生成 `draft` 结构化意向单，不把网页自由文本带入执行阶段。
2. 管理面显式 confirm/reject，不能用聊天里的自然语言确认代替鉴权动作。
3. 执行前再次检查预算、商户白名单、价格上限、过期时间和幂等 receipt；任一失败 fail-closed。
4. 首版 `auto_confirm_cap=0`，每笔都需人工确认；自动确认必须另立变更并重新安全评审。
5. 每次尝试都写 spend ledger 和只读观测；成功后才写 action trace，不以模型输出宣称成功。

## 6. 必须补齐的控制面与测试

- 管理面：desired/effective 开关、当前载体、额度、暂停状态、最近结果和失败原因；默认只读。
- 客户端：仅展示待确认意向单和结果，不保存支付凭据；无能力时明确降级为人工链接/提醒。
- 测试：57 soak 证据、账本写失败 fail-closed、重复 receipt 幂等、超预算/超价/过期拒绝、
  assistant_loop 无法 confirm、选品/执行模块静态隔离、Cloudflare sandbox challenge 校验。
- 跨仓接口若新增，必须同步 `docs/three-repo-interface-catalog.md` 及对应桌面/手机文档；未完成部分标记 `open`。

## 7. 交付顺序与准入结论

`A 修复观测 → A soak 30 天 → B 选择并小额配置载体 → 用户书面拍板 → C 评估/另立 adapter → D 人工确认 MVP`。

在此顺序完成前，本项目的正确行为是“观察余额、生成提醒、等待用户自行付款”，而不是自动充值或自动购物。
